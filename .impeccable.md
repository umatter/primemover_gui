# Impeccable Design Context — PrimeMover

## Design Context

### Users
PrimeMover is used by two roles working together on **algorithm / recommender-system studies** —
experiments where automated browser "bots" act as simulated users on platforms (e.g. YouTube) to
observe what content the platform's algorithm surfaces to different personas.

- **Principal Investigators (PIs)** — researchers / social scientists who *design* a study. Domain-smart
  but not necessarily technical. They need plain language, guidance, and confidence that the setup is
  correct. They think in terms of research questions, conditions, and simulated users — not crawlers,
  proxies, or multilogin profiles.
- **Research Assistants / Operators (RAs)** — more technical staff who *operate* studies: they set up
  many runs, tweak low-level settings, and monitor execution. They value speed, bulk actions,
  keyboard efficiency, and access to the raw plumbing the PI never sees.

Context: used at a desk during the workday, often over long sessions, on a laptop/desktop. The product
must serve a guided first-run for the PI and a fast power-mode for the RA — the same screens, different
depth.

### Brand Personality
Three words: **calm, scientific, trustworthy.** Voice: precise, measured, quietly authoritative — a
research instrument, not a marketing site. It explains without condescending, never hypes, and is honest
about state (a failed run says so plainly and calmly). PrimeMover has a **standalone product identity**
(not tied to an institutional/university brand). Emotional goal: the user feels *in control* and
*confident the data will be sound*.

### Aesthetic Direction
- **Theme: light.** Daytime, focused, long research sessions; light signals clarity and rigor.
- **Tone: refined-empirical.** Generous whitespace, strong typographic hierarchy, restrained palette with
  a single confident accent. Think a well-set research journal or a precision instrument's labeling —
  not a busy SaaS dashboard, not an admin CRUD grid.
- **Anti-references:** the current admin-tool feel (seven flat sortable tables, default indigo, system
  fonts); generic AI-SaaS look (cyan-on-dark, purple gradients, identical card grids, glassmorphism).
- **Type:** display serif **Spectral** (scholarly, calm, trustworthy) paired with grotesque UI face
  **Hanken Grotesk** (clean, legible, data-dense). Monospace reserved *only* for genuine machine values
  (correlation IDs `exp-…|cr-…|q-…|j-…`, status codes).
- **Color (OKLCH):** warm-cool paper neutrals tinted subtly toward the brand ink-blue; deep Prussian
  ink-blue as the primary/brand; one sparing warm **signal** accent (measured amber/ochre) for primary
  actions and active states; refined, desaturated status colors (success green / running amber / failed
  red) — never the harsh current `#b91c1c` / `#14532d`.

### Design Principles
1. **Hierarchy over inventory.** Present the study's real structure (Experiment → Bots → Runs → Jobs),
   never seven sibling admin lists. An Experiment *is* a project workspace.
2. **Plain language first, precision on demand.** Researcher-facing terms up front (a "crawler" is a
   *bot* / simulated user; agent + proxy + configuration are its *setup details*). Raw entities live
   behind "Advanced" disclosure and a power-user Library — demoted from primary navigation.
3. **Calm confidence.** Generous space, restrained color, one signal accent, strong type hierarchy.
   The UI should read as a precise instrument, not a crowded control panel. 60-30-10 by visual weight.
4. **Guide the first step, respect the hundredth.** A guided wizard with sensible defaults for setup;
   fast, keyboard-friendly, bulk-capable tools for the operator who does it daily.
5. **Trust through transparency.** Always show run status and progress honestly and calmly
   (succeeded / running / failed) with states that inform rather than alarm.
